# Build-time questions & unknowns for kho-ja v1 start

> Generated by a planning subagent from the locked decisions (DECISIONS.md, DESIGN.md,
> ARCHITECTURE.md, ROADMAP.md, DEVELOPMENT.md, package.json, provisional `src/`).
> These are **how-to-implement** questions — the content model is already locked.

## 1. Data Model / State Shape

- **Q1.1** Block union vs discriminated union for the two type-kinds (default vs
  custom). Single `Block` with `kind: 'default' | 'custom'`, or two types sharing a base?
  Shape of `values` for defaults vs custom (loose `Record<string, unknown>`)?
- **Q1.2** Where `placed: boolean` lives — on the Block, or a separate
  `placements: Map<BlockId, Vec>` where absence means "not placed"? (The latter is
  cleaner for library queries.)
- **Q1.3** OQ-10: how group membership is stored — a `members: BlockId[]` field on
  the group block, or a `GroupMembership { groupId, memberId }` edge table?
- **Q1.4** How the simple `Link { id, blockA, blockB }` is stored (top-level record,
  separate from future typed connections).
- **Q1.5** Shape of the type/schema registry (`types: Record<TypeId, TypeDefinition>`?
  Is TypeId a user string or generated? Can two types share a name?).
- **Q1.6** View state shape at three levels (type default + per-block override +
  named views): where `ViewDefinition` lives, how a block references its active view.
- **Q1.7** "One canonical block per thing": is the block ID the identity, or is there a
  separate asset concept? Does the side panel hold the same `Block` objects as the
  board, or a shadow copy?
- **Q1.8** Default type field definitions as code vs data (hardcoded TS field list vs
  JSON definition shipped by code).
- **Q1.9** Precise block-lifecycle state machine: created → placed → not-placed →
  permanently deleted (from side panel). What happens when a group that is itself not
  placed is deleted?
- **Q1.10** Exact File-Group-deletion cascade spec: iterate members, check each for
  other references (other groups or standalone placement), unplace if none.
- **Q1.11** ID generation strategy for future persistence/sync (UUID v7 vs nanoid vs
  custom).

## 2. Rendering / Canvas Engine

- **Q2.1** Canvas layer architecture: single transform `<div>` + overlay `<canvas>`
  for grid/edges/selection, or two sibling containers sharing viewport state?
- **Q2.2** Viewport culling implementation: `useMemo` filter vs `IntersectionObserver`
  vs virtual list; culling margin.
- **Q2.3** Background grid: Canvas API vs CSS pattern.
- **Q2.4** Link rendering: SVG overlay (simpler, pointer-events work) vs Canvas API
  (consistent with grid, but needs manual hit-testing).
- **Q2.5** Block size model: fixed per type, auto-height from content, or resizable?
  (Auto-height complicates culling.)
- **Q2.6** Selection model: single-select only, or multi-select (enables "select →
  group")?
- **Q2.7** `text` rich-text editor: textarea + markdown, contentEditable + manual
  parse, or a library (Tiptap/Milkdown/Lexical)? "Generic edit path for v1."
- **Q2.8** File Group block sizing across card/list/grid views (does block resize on
  view switch?).
- **Q2.9** Drop target for "paste files into a File Group" (OS drag onto group block vs
  panel selection vs menu action).
- **Q2.10** Does the viewport/culling architecture accommodate a future minimap /
  zoom-to-fit?

## 3. Architecture

- **Q3.1** Module/folder structure for the rewrite (core/engine + types + canvas +
  blocks + schema + panel + views + store).
- **Q3.2** OQ-6 monorepo flavor: single app with clean separation vs workspaces.
  (npm only, no pnpm.)
- **Q3.3** State management: single `useReducer` vs a lightweight store (Zustand/Jotai);
  subscription granularity for re-render performance.
- **Q3.4** Where "uniform base + layered defaults" lives in code (BlockEngine wrapper
  vs state-layer generic logic + pluggable renderers).
- **Q3.5** Type-creator UI location (modal vs panel tab vs page).
- **Q3.6** Side panel architecture (fixed panel vs overlay vs tab; own viewport/scroll;
  drag-to-place mechanism).
- **Q3.7** Toolbar structure (always-visible vs contextual vs split).
- **Q3.8** CSS strategy (plain co-located CSS vs CSS Modules vs Tailwind vs CSS-in-JS).
- **Q3.9** Component boundaries / tree depth (App > Layout > { SidePanel, Toolbar,
  Board > Canvas > BlockRenderer }).

## 5. Open Build-Time Decisions

- **Q5.1** OQ-6 monorepo — resolve now or defer (agent recommends single app for v1).
- **Q5.2** OQ-9 asset store — is the "asset store" just the `blocks` record, or a
  separate `assets` collection in v1 (metadata-only)?
- **Q5.3** OQ-10 container mechanism — containment as field on group vs edge table vs
  general `parent` field on every block.
- **Q5.4** OQ-13 persistence & schema versioning — add a `version` header to the state
  now (zero cost) or wait for persistence.
- **Q5.5** OQ-14 edge/link lifecycle on deletion — do links reference placements (cascade
  on unplace) or canonical blocks (persist)?
- **Q5.6** OQ-3 view field exposure — lock "views select fields, never demand new
  fields" as a v1 rule.
- **Q5.7** Custom schema editing UX — can a type's schema be edited after creation?
  What happens to existing blocks (never-destroy-data rule)?
- **Q5.8** How named views are persisted (on type vs on board) and how users switch
  to them.
